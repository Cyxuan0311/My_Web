目前，**llama.cpp 对 PD 分离的支持尚处于积极的开发和规划阶段**，还未在主线版本中完全实现。不过，开发者社区已经明确了技术路线图，并且核心的底层能力已经就绪。

### 🛠️ 实现计划：从单进程到分离式架构

llama.cpp 计划通过改造 `llama-server` 来实现 PD 分离。

它的核心思路是**将原来一个进程内同时处理 Prefill 和 Decode 的单一 `llama_model`，拆分成多个各司其职的实例**。

*   **专用实例**：为 Prefill 和 Decode 任务分别创建独立的 `llama_model` 实例。
*   **设备分配**：用户可以为这些实例灵活配置不同的计算设备，比如用一个实例专门在 GPU 上做 Prefill，用另一个在 CPU 上做 Decode。
*   **远程设备支持**：最关键的是，这些设备可以是 **RPC（远程过程调用）设备**。这意味着 Prefill 和 Decode 完全可以跑在**不同的物理机器**上。

### 🔑 关键组件：实现分离的三大基石

这套方案建立在三个关键组件之上：

1.  **`llama_state_` API：KV Cache 的搬运工**
    这是实现分离的**核心基础**。Prefill 阶段计算完成后，通过 `llama_state_get_data()` 获取 KV Cache 数据，然后利用此 API 将其传输给 Decode 实例。

2.  **任务流水线：拆分与调度**
    需要将一个完整的推理任务拆分为两个阶段：
    *   **Prefill 任务**：提交给 Prefill 实例处理。
    *   **Decode/生成任务**：Prefill 完成后，将包含 KV Cache 的**任务状态**提交给 Decode 实例继续生成。

3.  **网络与内存缓存：连接物理设备**
    在远程分离的场景下，KV Cache 需要在网络中传输。
    *   **高速网络是关键**：传输性能是系统瓶颈，低延迟网络至关重要。
    *   **主机内存作为缓存**：KV Cache 在传输前后，可能会暂存在主机内存的“Prompt Cache”中。

### 🤔 当前挑战与待解决问题

在实现过程中，llama.cpp 还需要解决一些关键问题：

*   **模型复制与内存效率**：最简单的方式是在 Prefill 和 Decode 节点上**各自加载一份完整的模型副本**。虽然实现简单，但内存开销大。更优的方案是探索模型分片或共享内存等技术。
*   **上下文间 KV Cache 共享**：需要确保 KV Cache 数据能在不同的 `llama_context` 之间安全、高效地传递。
*   **序列化开销**：KV Cache 在传输前需要被序列化，这个过程本身会引入额外的计算和延迟开销。

### 💎 总结

总的来说，llama.cpp 的 PD 分离可以看作一套**基于 RPC 的分布式推理方案**。它通过将 Prefill 和 Decode 部署到不同的物理设备上，来解决资源冲突问题。

虽然完整功能尚未上线，但核心的 `llama_state_` API、RPC 设备支持等基础设施已经具备。未来的工作将聚焦于任务调度、网络传输优化和内存效率的提升，这些在官方的 Issue 和讨论中都有明确的规划。
